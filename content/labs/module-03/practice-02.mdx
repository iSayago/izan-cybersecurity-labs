## Objetivo

Comprobar qué información registra IIS sobre una petición web y localizar en el log la cadena de una inyección SQL realizada contra LuxuryTreats.

## Contexto y entorno del laboratorio

El sitio LuxuryTreats está alojado en IIS sobre la máquina `WebServer2022`. La práctica configura el registro W3C del sitio, selecciona campos útiles para el análisis y revisa el archivo generado en la carpeta de logs. La petición se genera desde la máquina atacante Ubuntu mediante Firefox.

## Herramientas utilizadas

| Herramienta | Uso real en la práctica |
| --- | --- |
| IIS Manager | Configuración del logging y de los campos W3C |
| Notepad++ | Apertura y búsqueda en el archivo de log |
| Firefox | Generación de la petición SQLi desde la máquina atacante |
| LuxuryTreats | Aplicación web de laboratorio |

## Procedimiento realizado

1. En **IIS Manager** se abre el sitio **LuxuryTreats** y se entra en **Logging**.
2. Se confirma que el formato es **W3C** y se revisa la carpeta de destino:

```text
C:\inetpub\logs\LogFiles\W3SVC2
```

3. En **Select Fields** se añaden campos útiles: `c-ip`, `cs-username`, `sc-status`, `sc-substatus`, `sc-bytes`, `cs-bytes`, `cs-host`, `cs(User-Agent)`, `cs(Cookie)` y `cs(Referer)`.
4. Se aplica la configuración y se genera una petición SQLi contra `OrderDetail.aspx`.
5. Se abre el archivo `u_ex...log` con Notepad++ y se busca la cadena `1=1;--`.
6. Se identifica la línea que contiene el parámetro manipulado y se leen sus campos.

## Análisis de resultados

**Observado:** el archivo de IIS contiene la petición con el parámetro `Id=ORD-001%27or1=1;--`, el usuario `bob`, la IP de la máquina atacante y un estado HTTP 500. La aplicación devolvió un error en esa solicitud, pero el intento quedó registrado.

**Interpretación:** el log web conserva la entrada completa y permite reconstruir qué se envió, desde dónde y con qué identidad. La codificación URL (`%27` por `'`) no oculta el patrón; el analista debe decodificarla. El estado 500 puede ser una señal de error de aplicación, no la prueba de que la inyección tuviera éxito.

Este ejercicio conecta con la práctica de SQL Injection: la misma cadena que se veía en la URL aparece en el servidor. La diferencia es que ahora hay una fuente persistente y centralizable para detección y correlación.

## Conclusiones

Los logs de IIS son útiles si se seleccionan campos suficientes. Un log por defecto puede decir poco; añadir usuario, host, agente y query permite investigar. La lección es revisar la codificación, no confiar en el código de estado como única señal y conservar el contexto de la petición.

## Aprendizajes

- Los campos seleccionados determinan la utilidad futura del log; conviene configurarlos antes de necesitarlos.
- La query codificada debe decodificarse y revisarse junto con el estado HTTP y la identidad.
