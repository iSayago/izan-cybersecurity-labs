## Objetivo

Comprobar si el formulario de contacto de LuxuryTreats valida el contenido introducido por el usuario o si permite que un bloque `<script>` se ejecute en el navegador de otra persona.

## Contexto y entorno del laboratorio

La prueba se realiza en la página **Contact** de la aplicación de laboratorio, dentro de la misma máquina atacante Ubuntu utilizada en el ejercicio anterior. Se utiliza un correo de prueba y el campo **Comment** del formulario. La grabación no muestra una víctima distinta ni una sesión de otra persona: la ejecución se comprueba en el propio navegador del analista.

## Procedimiento realizado

1. Se abre la página `Contact` y se rellena el campo **Email** con una dirección de prueba.
2. En el campo **Comment** se introduce un bloque JavaScript con una llamada a `alert`.
3. Se pulsa **Save Comment**.
4. El navegador muestra el diálogo `You are hacked`, lo que confirma que el contenido se interpretó como código y no como texto.

```html
<script>alert('You are hacked');</script>
```

La grabación muestra el diálogo después de guardar el comentario. No se ha ejecutado ninguna acción posterior sobre la sesión; la prueba se limita a demostrar la ejecución del script.

## Análisis de resultados

**Observado:** el formulario acepta el bloque `<script>` y, al guardar, el navegador ejecuta `alert('You are hacked')`. El texto no se muestra como caracteres literales: se interpreta como HTML/JavaScript.

**Interpretación:** existe una vulnerabilidad de Cross-Site Scripting. La prueba utiliza un `alert` inocuo; en un escenario real, el mismo punto de entrada podría intentar leer el DOM, manipular la interfaz o realizar acciones en nombre de la sesión. El alcance exacto (XSS reflejado o almacenado) no se determina en la grabación, por lo que no se afirma esa clasificación.

El IoC visible es la presencia de etiquetas `<script>` o manejadores de eventos en campos que deberían ser texto. La validación debe aplicarse en entrada y en salida, con codificación contextual y una política de seguridad de contenido adecuada.

## Conclusiones

Un formulario que funciona correctamente para un usuario legítimo puede seguir siendo inseguro: el problema aparece cuando el contenido se interpreta como código. La práctica muestra la diferencia entre "guardar un comentario" y "ejecutar un comentario", y por qué la validación debe cubrir todos los campos y contextos de salida.

## Aprendizajes

- La validación de entrada debe acompañarse de codificación contextual en la salida.
- Un `alert` demuestra ejecución, pero el alcance del impacto requiere analizar la sesión y el almacenamiento del contenido.
